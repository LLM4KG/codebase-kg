## What this measures, and what it cannot

`docker/apply_edits.js` is **all-or-nothing**: edits stage in memory and one failed
SEARCH aborts the whole script. That is right for the harness — a half-applied script
produces build errors describing a state the model never asked for — but for
*measurement* it collapses "three of four edits were correct" into `never_applied`.

So WP12's matched totals are **upper bounds on the damage a thin context did, not
measurements of it**. M1 below says how wide that bound is *in candidates*. Turning it
into a pass count needs `scripts/wp12_per_edit_replay.py` (step 9); nothing on this
page moves a pass count.

Corpus: **420 candidates** across 8 runs (2026-09-18_wp5_p1p3, 2026-09-19_wp5_p1p3_baselines, 2026-09-19_wp5_p4p6, 2026-09-21_wp12_matched, both legs), all `output_format = search_replace`.

### Gate: the Python mirror against the recorded results

`src/evaluation/edit_replay.py` transliterates the applier, differing in exactly one
respect: it records a verdict and continues where the JS aborts. It is licensed by a
differential gate that runs on every invocation of this script —
for all **420** candidates the mirror's predicted first failure equals the
`apply_reason` the harness recorded, and "no failure" equals "stage is not
`diff_apply_fail`". **0 mismatches.** Step 9 cross-checks a further
52 of them against the real Node applier inside Docker.

## M3 — corrected retention: is the retrieved set sufficient?

WP12's retention asks *is every file the reference patch edited still in the context?*
Where a task admits more than one solution layer that question mis-measures adequacy.
The column beside it asks instead: **does the retrieved set contain some witnessed
passing solution?** A witnessed solution is the edited-file set of any passing
candidate anywhere in the corpus, minus paths absent at the pinned commit — a file the
task *creates* is unretrievable by construction.

**This is survivorship-biased by construction and is a lower bound on adequacy.** A
solution counts as witnessed only because some arm happened to retrieve enough to find
it; solutions no arm found are invisible here. `sufficient = False` therefore means
"no *known* solution fits", never "no solution exists".

It is also **not** a predictor of passing. P4's matched cells are sufficient under this
test and still passed 0/5 on the Claude leg — the files were there and the models did
not use them. Sufficiency bounds what retrieval can be blamed for; it does not claim
the rest.

## What this does not show

- **No pass count moves.** M1 counts candidates with a surviving edit, not passes. A
  candidate whose kept edits are the whole fix and one whose kept edits are cosmetic
  are one row each here; only step 9 tells them apart.
- **M1 is not a proposal to change the applier.** All-or-nothing stays exactly as
  published, or WP5 comparability breaks.
- **M3 cannot see unwitnessed solutions** (above), and is not evidence that a
  sufficient context produces a pass.
